How we cut our Postgres bill by 40%

Platform team · 9 min read

Eighteen months ago our managed Postgres spend was the second largest line on the infrastructure bill, right behind compute. Nobody had looked at it in a while because nothing was on fire. When we finally sat down with the numbers, most of the money was going to capacity we did not use and to work the database was doing for no reason.

This post walks through what we changed, in the order we changed it, and what each step saved. None of it is clever. That is sort of the point.

1. Measure before touching anything

We started by pulling two weeks of metrics for every cluster: CPU, memory, IOPS, connections and storage growth. The pattern was the same almost everywhere. Primaries sat at 15 to 25 percent CPU at peak, and read replicas were barely awake.

ClusterInstancePeak CPUPeak connections
billingdb.r6g.4xlarge22%1,840
eventsdb.r6g.2xlarge31%960
accountsdb.r6g.2xlarge14%2,210

The connection counts were the surprise. They explained why the instances had been sized up in the first place: memory pressure from thousands of idle backends, not query load.

2. Put PgBouncer in front of everything

Each Postgres backend costs several megabytes of memory even when idle. Our services opened a pool per pod, and with autoscaling that meant thousands of mostly idle connections. We moved every service to PgBouncer in transaction mode.

[pgbouncer]
pool_mode = transaction
max_client_conn = 5000
default_pool_size = 40
server_idle_timeout = 60

Server-side connections dropped from about 2,000 to under 150 on the largest cluster. Memory headroom went from "worrying" to "boring", which made the next step possible.

3. Right-size the instances

With pooling in place we dropped each primary one instance size and watched for a week. Then we did it again where the numbers allowed. Billing went from a 4xlarge to an xlarge. Accounts went from a 2xlarge to a large.

Rule of thumb we ended up with: size for p99 CPU at 60 percent, not for connection count.

4. Drop the indexes nobody uses

Unused indexes cost storage, slow down writes and inflate WAL, which in turn inflates replica and backup costs. This query lists indexes with zero scans since the last stats reset:

SELECT schemaname, relname, indexrelname,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;

We found 61 GB of indexes on the events cluster that had not been read in over a year. Three of them were duplicates of the primary key with a different name. Dropping them cut write IOPS by about a fifth.

5. Move cold data out

About 70 percent of the events table was older than 90 days and only ever read by a monthly report. We partitioned by month, moved partitions older than 90 days to object storage as Parquet, and pointed the report at the warehouse instead. Storage on that cluster dropped from 3.1 TB to 900 GB.

The pooling change did not save money on its own, but every other saving depended on it. If you only do one thing from this post, do that one first.
